## 1. Purpose

The VM has three jobs and one prohibition.

**Jobs.**

1. **Execute the bytecode of [`07-bytecode.md`](07-bytecode.md) correctly**, for every program the
   M4 compiler can produce, on every input.
2. **Be faster than CPython 3.13**, on the aggregate of `bench_core`, and never slower than CPython
   on any single benchmark in that group. The gate is stated in
   [`00-blueprint-review.md`](00-blueprint-review.md) §4 and restated with the measurement protocol
   in §12.2.
3. **Never abort the process.** No panic, no `unwrap` on user data, no arithmetic overflow, no
   out-of-bounds access, no `unsafe` precondition reachable from a script. Every failure is a
   catchable `ZenError`. This is a hard rule with a full enumeration in §4, and it is the single
   most important property of this document.

**The prohibition.** Zen 2.2.0 can `panic!` from user-reachable code. `deref_cells` carries an
unconditional `panic!` for a cyclic `Value::Cell` chain at `src/runtime.rs:225`, reachable from a
script that builds a self-referential closure. That is a process abort, and it is exactly the class
of failure [`00-blueprint-review.md`](00-blueprint-review.md) §5 exists to eliminate. The
M4 compiler removes the *cause* (§9.1 of [`07-bytecode.md`](07-bytecode.md) proves single-level
cells, so the chain cannot form), and §4 removes the *possibility* by making the VM's failure modes
explicit and total.

The workspace already commits to half of this: `panic = "unwind"` and `overflow-checks = true` in
the release profile (`zen/Cargo.toml:57-58`), with the comment pointing at the stability rules. This
document is the other half — it says what the VM does *instead* of panicking.

## 2. The `Vm` struct and the register file

### 2.1 The struct

```rust
//! zen-vm/src/vm.rs

use std::sync::Arc;

/// The interpreter. One `Vm` per OS thread. Not `Send`: see §2.5.
pub struct Vm {
    /// ── the register file ────────────────────────────────────────────────
    /// Exactly `NUM_REGS` slots. A frame owns a contiguous slice of this
    /// array; locals, temporaries and the call window are all registers
    /// (§2.2). 256 × 8 bytes = 2 KiB, allocated once, never reallocated.
    registers: [Value; Vm::NUM_REGS],

    /// ── control state ────────────────────────────────────────────────────
    /// Call frames, innermost last. `Vec`, `reserve`d to `max_depth` when the
    /// VM is created so a push never reallocates on the hot path.
    frames: Vec<Frame>,
    /// Bytecode pointer for the **innermost** frame. Cached here so the
    /// dispatch loop's fetch is `*code.add(pc)` with no frame dereference.
    ip: u32,
    /// The saved `ip` of the frame we are returning *into*, used by `RETURN`.
    return_ip: u32,

    /// ── handler stack (try/catch, §8 of 07-bytecode.md) ────────────────
    /// Active `HandlerCursor`s, innermost last. Preallocated with `frames`.
    handlers: Vec<HandlerCursor>,

    /// ── per-thread scratch, all preallocated ─────────────────────────────
    /// The blueprint lists an "operand stack". **Zen has none** — see §2.4.
    /// What remains is three fixed-capacity buffers:
    ///   * `native_args` — staged arguments for a `NativeFn` that needs an
    ///     owned slice (the v2 ABI, §8.3). Capacity 16, the largest builtin
    ///     arity. Borrowed by the v1 ABI, so usually untouched.
    ///   * `spill` — the single-slot save area used by `MAKE_CLOSURE` when its
    ///     upvalue sources alias the destination (§9.1 of 07-bytecode.md), and
    ///     by the deopt record buffer in M11.
    ///   * `exc_payload` — the in-flight error value during an unwind, and
    ///     the single `Value` an error owns while it is being constructed.
    native_args: Vec<Value>,
    spill: [Value; 8],
    exc_payload: Value,

    /// ── program data ─────────────────────────────────────────────────────
    /// Every `FunctionProto` in the loaded module set, flat. `Instruction`s
    /// index this; a proto index is a `u32`, and a `FunctionProto*` is a raw
    /// pointer into it so the dispatch loop never does a bounds check on a
    /// proto lookup.
    protos: Vec<Arc<FunctionProto>>,
    /// Interned identifier and string tables, shared with the compiler so a
    /// field name is a `u32` on both sides.
    names: Arc<str_table::Interner>,
    strings: Arc<str_table::Interner>,

    /// ── globals and modules ──────────────────────────────────────────────
    globals: Vec<Value>,            // dense, indexed by interned name id
    globals_by_name: ahash::AHashMap<u32, u32>,
    modules: ahash::AHashMap<Arc<str>, ModuleHandle>,

    /// ── inline caches (§6) and shapes (§7) ──────────────────────────────
    /// One entry per `IcSite` in every loaded proto, in the same order. The
    /// `IC_*` opcodes index this directly, so a hit is one load. Always
    /// monomorphic-shaped: a promoted entry points into `ic_poly`.
    ic: Vec<InlineCache>,
    /// Side table for the rare polymorphic sites (§6.3). Bounded: 1024
    /// entries, and a site that wants more goes megamorphic rather than
    /// growing this. Empty and untouched in M4, allocated for M5.
    ic_poly: Vec<[InlineCache; 2]>,
    /// The shape table. Append-only: a `ShapeId` is an index and is never
    /// reused, which is what makes a stale IC tag a miss rather than a wrong
    /// answer.
    shapes: Vec<Shape>,
    /// `shape -> shape` transition edge cache, for `d[k] = v` on a new key.
    shape_transitions: ahash::AHashMap<(ShapeId, u32), ShapeId>,

    /// ── natives and builtins (§8) ────────────────────────────────────────
    natives: Vec<NativeEntry>,

    /// ── limits and diagnostics ───────────────────────────────────────────
    max_depth: u32,
    step_budget: u64,          // REPL single-step; `u64::MAX` when running
    debug_pause: DebugPause,   // REPL / inspector
    /// `zen-perf` counters, compiled in under the `zen-perf` feature (§12.4).
    /// Zero-sized and elided otherwise, so the release build pays nothing.
    perf: PerfCounters,

    /// One `Value` per in-flight Zen call, for the REPL's frame inspector.
    /// `None` outside the REPL.
    inspector: Option<InspectorState>,
}

impl Vm {
    /// ── register count: THE ruling ───────────────────────────────────────
    /// 256, because that is what a `u8` operand field addresses. See §2.3.
    pub const NUM_REGS: usize = 256;
    /// Registers a single function may use (§2.3 of 07-bytecode.md).
    pub const MAX_FRAME: usize = 250;
    /// Default call-depth limit. Chosen so that `frames` (24 B each) plus
    /// `handlers` (4 B each) is under 512 KiB and the interpreter's own
    /// *native* stack, which grows by ~200 B per Zen call in debug builds,
    /// stays inside an 8 MiB thread stack.
    pub const DEFAULT_MAX_DEPTH: u32 = 8192;
}
```

### 2.2 The register file, the window, and what a frame owns

There is **one flat array**. A frame does not own registers; it owns a **base offset** into the
shared array.

```rust
/// One active Zen call.
#[derive(Clone, Copy)]
pub struct Frame {
    /// The executing function's proto. A raw pointer, not an index, so the
    /// dispatch loop reads `proto.code.as_ptr()` once per call and then never
    /// touches the pointer again. Valid for the VM's lifetime: protos are
    /// `Arc`-held in `vm.protos` and are never removed while a frame is live.
    proto: *const FunctionProto,
    /// Bytecode pointer, cached in the frame as well as in `vm.ip` so a
    /// `RETURN` restores it without a division.
    code: *const Instruction,
    /// First register this frame owns: `&vm.registers[base]`.
    base: u16,
    /// Current instruction index within `code`.
    pc: u32,
    /// One past the last register this frame owns: `base + proto.frame_size()`.
    /// Every window opcode's underflow check compares against this.
    window_end: u16,
    /// First register of the *callee's* window, restored by `RETURN`.
    caller_base: u16,
    /// The `vm.ip` to resume at after this frame returns.
    return_ip: u32,
    /// Innermost live handler in this proto's exception table.
    handler_base: u16,
    /// Number of upvalues this closure owns. Also the count of open upvalues
    /// the unwinder must close (§8 of 07-bytecode.md).
    upvalue_count: u8,
    /// `true` if this frame is a tail-call target and can be replaced in place.
    is_tail: bool,
}
```

A function's registers are laid out as:

```text
        base + 0                base + params.len()     base + num_locals
        ├──────────────────────┼───────────────────────┤
        │  params (0..P)       │  named locals (P..L)  │  temporaries (L..F)
        │  = the call window   │                       │  = the free list
        └──────────────────────┴───────────────────────┴
                                                            ← window_end
```

- **Locals *are* registers.** There is no separate locals array and no load/store opcode pair
  distinct from ordinary moves; reading a local is reading a register at a fixed offset. This is the
  single biggest structural difference from the old runtime, whose `CompiledFunction` had a
  separate `local_count` and a stack (`src/bytecode.rs:186`).
- **The call window is at register 0**, because arguments arrive in registers 0..argc of the callee
  by the convention of §2.5 in [`07-bytecode.md`](07-bytecode.md). So `self` is register 0 in a
  method, exactly as `compile_method` arranges it in the old tree
  (`src/bytecode.rs:241-246`).
- **The free list is the tail**, and its depth at any `pc` is the number of temporaries live at that
  `pc`. The M9 GC's root map is "registers `base..base+frame_size` of every live frame", which is
  why the register discipline in [`07-bytecode.md`](07-bytecode.md) §6.2 was chosen for its
  simplicity rather than its density.

### 2.3 How many registers, and why 256

**Ruling: 256 register slots, allocated once per `Vm`.** The trade-off was argued explicitly, since
"64 might be faster" is a real position.

| Option | For | Against |
|---|---|---|
| **256 (`u8` field)** | Matches the operand encoding exactly, so no instruction is ever a wide form. No limit a user can hit without writing 250+ live bindings in one scope. | 2 KiB of array, 4× the cache footprint of a 64-register file. |
| **64 (`u16` field, 2 bytes per operand)** | 512-byte register file; the hot working set of a typical function is 8–20 registers either way, so the *touched* footprint is identical. | The instruction becomes 8 bytes, halving instruction density. The blueprint's `[op: u8 \| a: u8 \| b: u8 \| c: u8]` is exactly right on this point, and every fast register VM in existence uses a byte per operand. |
| **32** | Fits one 256-byte cache line. | A function with 32 bindings fails to compile. Unacceptable. |
| **Adaptive (grow the file per frame)** | Small frames get a small file. | Breaks the "one flat array, `base` is an offset" model, forces a bounds check on every register access, and makes the JIT's frame descriptor frame-dependent. |

**Why 64 is not faster, in detail.** The array size is not what costs time; the number of *touched*
lines is. A `while` loop over a list with an accumulator touches registers 0–5, so both a
64-entry and a 256-entry file read 48 bytes — **one cache line**. The remaining 30 KiB of a
256-entry file is never read, never in cache, and never costs a miss. Meanwhile the 64-entry design
pays a real cost on every single instruction: `a` and `b` are `u16`, so the fetch is an 8-byte load
and the operand extraction is a 16-bit load each instead of a mask of a register already in a
register. On a dispatch-bound VM the fetch path is *the* hot path.

There is a second, subtler reason 256 wins: **register indices are 8-bit, so a register index fits
in a `mov r8, imm8` on x86-64.** With `u16` indices the VM's register accesses compile to
`movzx` + a wider addressing mode on every single operand, and the M11 translator's machine code
gets a frame-pointer-relative `u16` displacement everywhere instead of an `i8`/`i32`. That is a
throughput cost in the interpreter *and* a code-size cost in the JIT, for a cache benefit that does
not materialise because the high registers are never touched.

**What would change the ruling.** If a profile ever showed the 2 KiB array itself being a problem —
which would require a function touching > 64 registers in a loop — the fix is not a smaller array,
it is a spilling pass (`--opt-regalloc`, [`07-bytecode.md`](07-bytecode.md) §6.2), which reduces
the *high-water mark* without changing the encoding. This ruling is on the §13 list for exactly that
reason.

### 2.4 There is no operand stack, and the blueprint's "operand stack" field is wrong

The blueprint lists a preallocated operand stack in the VM state. A register machine with a register
window (§2.2) has no push or pop: arguments are *already* in the callee's registers and results go
*directly* to a named destination. The three buffers that survive in the struct above exist for
specific, named reasons and none of them is "the stack":

| Buffer | Why it exists | Cost on the hot path |
|---|---|---|
| `native_args` | The v2 native ABI (§8.3) takes `&mut [Value]` for variadic builtins. Capacity 16, reserved at VM creation. | **Zero** for the v1 ABI, which passes `&[Value]` straight into the callee's register window. |
| `spill` | `MAKE_CLOSURE` may alias its destination with an upvalue source (§3.10 of [`07-bytecode.md`](07-bytecode.md)), so the sources are read into an 8-slot buffer first. | 8 stores and 8 loads, only for closures with ≤ 8 upvalues. |
| `exc_payload` | One `Value` slot for the in-flight error during an unwind. | Zero unless an error is being raised. |

Removing the operand stack removes roughly one push and one pop per three instructions. On a
dispatch-bound VM at ~4 ns/instruction, that is the difference between a stack VM and a register
VM, and it is the concrete content of the blueprint's "40 % fewer instructions" claim being
*misattributed* in [`00-blueprint-review.md`](00-blueprint-review.md) §A5.

### 2.5 `Vm` is not `Send`

`registers` is a raw array and `Frame` holds `*const FunctionProto`. Making the `Vm` `Send` would be
unsound as stated. The M10 concurrency model does not need it: each Zen thread owns its own `Vm`
([ADR-0003](decisions/ADR-0003-concurrency-semantics.md)), and `spawn` creates one. `Vm` is
explicitly `!Send` and `!Sync`, enforced by a static assertion in the crate, and the thread-safety
boundary is the *value* level (`Arc<Mutex<T>>` for `shared` bindings), never the VM.

## 3. The dispatch loop

### 3.1 The shape of the loop

The loop is a single `loop` over a raw instruction pointer with one `match`. There is no inner
function per opcode, no `Result` in the happy path, and no per-instruction bounds check.

```rust
// zen-vm/src/exec.rs

impl Vm {
    /// Execute until the frame stack is empty (a module completes) or the
    /// REPL's step budget is exhausted.
    pub fn run(&mut self) -> VmResult<()> {
        'outer: loop {
            if self.step_budget == 0 {
                return Ok(());                       // REPL step limit (§10)
            }
            self.step_budget -= 1;

            let code = self.code_ptr();               // `self.frames.last().code`
            let pc = self.ip as usize;

            // SAFETY: `ip` is always an index into a live frame's code array,
            // and is only ever assigned from a `pc + 1` where that `pc` was
            // itself a valid index, or from a validated jump target at load
            // time. `validate_jump_targets` (§11.2, test 9) proves the latter
            // for every loaded image.
            let inst: Instruction = unsafe { *code.add(pc) };

            self.ip = pc as u32 + 1;

            match inst.op {
                Op::LOAD_CONST => { self.regs_a(inst) = self.const(inst.b); }
                Op::ADD => self.exec_add(inst),
                Op::JMP_BACK => {
                    // Only instruction that writes `ip` backwards.
                    self.ip = self.rel_target(inst.b);
                    continue 'outer;
                }
                Op::CALL => { self.exec_call(inst)?; }
                Op::RETURN => {
                    self.exec_return(inst)?;
                    if self.frames.is_empty() { return Ok(()); }
                    continue 'outer;
                }
                Op::THROW => return Err(self.raise_throw(inst)),

                // ── the 100 remaining arms ──────────────────────────────
                // …

                // Mandatory. `op` is a `u8` and only 111 of 256 values are
                // defined; without this arm Rust emits a bounds check on the
                // jump table and a corrupted image panics instead of
                // producing a clean error. See §4.2.
                _ => return Err(self.bad_opcode(inst, pc)),
            }
        }
    }
}
```

**Why `self.ip = pc + 1` before the match.** Every opcode that is not a jump wants the next `pc`
already in place, so writing it once before the dispatch costs one store on the common path and
saves every arm from doing it. Only `JMP`, `JMP_IF_*` and `JMP_BACK` overwrite it.

### 3.2 Register access, and the 0 % bounds check

```rust
impl Vm {
    /// Register `base + a`. `a` is a `u8`, so the sum cannot exceed `u16::MAX`
    /// only because `base <= 250`; the compiler is told so explicitly.
    #[inline(always)]
    fn reg(&self, i: u8) -> Value {
        let base = self.frames.last().unwrap_or(&self.root_frame).base;
        // SAFETY: validated at load time (§11.2, tests 9–11) that every
        // register operand in every instruction of every loaded proto is
        // < proto.frame_size(), and that every frame's base + frame_size
        // <= NUM_REGS. This is the single load-time proof that replaces
        // every bounds check on the hot path.
        unsafe { *self.registers.get_unchecked(base as usize + i as usize) }
    }
}
```

That `get_unchecked` is the most dangerous line in the VM, so the contract is stated in one place
and enforced in one place, and **every other register access in the crate goes through this
function** — enforced by a crate-level lint (§3.5) that forbids `registers[i]` and
`registers.get_unchecked(..)` anywhere else. A raw index in the crate is a build failure, not a
review comment.

Three independent things have to be true for the `get_unchecked` to be sound, and each has a test:

1. Every register operand `< proto.frame_size()`. Checked by `Validator::validate` at load
   time — the same pass in [`07-bytecode.md`](07-bytecode.md) §4.2 that rejects out-of-range
   operands at **compile** time. The load-time pass is not redundant: it runs on `.zeno` files,
   which may come from another build.
2. `base + frame_size <= NUM_REGS`. Guaranteed by the call-window checks in `exec_call`
   (`window_end <= NUM_REGS` is a hard `err!`, not a debug assert) and by `DEFAULT_MAX_DEPTH`
   being small enough that `frames.len() * MAX_FRAME < NUM_REGS` can never be true — a Zen call
   never reallocates the register file.
3. `frames` is never empty when `reg` is called. The root frame (the module body) is pushed in
   `run`'s prologue, so `frames.last()` is `Some` in the loop body; the `unwrap_or(&self.root_frame)`
   makes that a compile-time-resolvable branch rather than an `unwrap`.

### 3.3 Why `match`, and not computed goto

The blueprint's dispatch table is presumably a "jump table" of function pointers. In stable Rust
that is not available: `match` on a `u8` is how you get one.

| Technique | Available in stable Rust? | Verdict |
|---|---|---|
| `match inst.op { ... }` | yes | **Chosen.** LLVM emits a bounds-checked jump table over the dense arms and a comparison chain or a second table over the sparse ones. |
| Computed `goto` (`asm!` / `goto *%rax`) | no, and not planned | Would need inline assembly per opcode. Rejected. |
| `become` (Armv9.5) / tail calls per opcode | no | Would need nightly `-Z` flags and would break the borrow checker on `&mut self`. |
| A `fn(&mut Vm, Instruction)` table | yes, but **4× slower [E]** | Every call passes `&mut self` and the instruction through the ABI, so nothing stays in registers across a dispatch. This is what a naive implementation does and it is a well-known trap. |
| Tail-threaded dispatch (`return self.step()`) | yes | Recursion in the compiler's view; LLVM turns it into a loop, but it prevents keeping the instruction pointer in a register. Rejected. |

**PGO, which is the actual answer to the indirect-branch problem.** A `match` on a hot opcode mix
is an indirect branch, and an indirect branch's cost is entirely a function of how well the CPU's
branch-target buffer predicts it. Zen's opcode mix is *extremely* skewed — in every real program,
a handful of opcodes (`LOAD_CONST`, `MOVE`, `CALL`, `JMP_BACK`, `GET_INDEX`) are 70–85 % of
executions **[E]**. So the dispatch loop is built with `-Cprofile-generate` in CI,
`-Cprofile-use` for release, and LLVM's branch-weight annotations put the hot arms physically
first. Concretely:

- `#[cold]` on every error path, every `raise_*` helper, and the `_ =>` arm, so those blocks are
  moved out of the loop body rather than interleaved with it.
- `Op::THROW`, `Op::RERAISE` and the native-arity error are `#[cold]` **arms** — the arm, not just
  the callee — so the hot path never has a taken-not-taken branch for them.
- The CI profile corpus is the full `tests/cases/` set plus the M3 differential runs, so the
  weights come from Zen code and not from a synthetic loop.

**The cost model, so the §12 targets are not a guess.** On a modern x86-64 core, a well-predicted
indirect branch is ~1 cycle, a mispredicted one is ~15–20 **[E]**. If PGO holds the misprediction
rate at 3 % of dispatches, dispatch costs ~1.6 cycles. Every other operation in the loop — the
4-byte load, the `ip` store, one register read and one register write — is 1 cycle each and
pipelined. That gives ~4–6 cycles per instruction, or **1.3–2.0 ns at 3 GHz [E]**, against CPython
3.13's ~40–80 ns for a comparable operation. Everything else in this document is about protecting
that 4–6 cycle budget.

### 3.4 The opcodes that are not one-liners

Most arms are three lines. These are not, and each is listed with the invariant it maintains.

| Opcode | What it actually does | Invariant |
|---|---|---|
| `CALL` | Push a frame: read `R[base+0..argc]` as the arguments, `MOVE` them to the callee's window, push a `Frame`, set `ip = 0`. | Window underflow is a hard error. Arg count mismatch is resolved by the defaults thunk ([`07-bytecode.md`](07-bytecode.md) §10.4), never by zero-filling. |
| `TAIL_CALL` | Copy the callee frame **over** the current frame, keeping `caller_base` and `return_ip`. Bounded by `tail_depth` so a `return f()` loop cannot grow the frame stack — it is a loop, not unbounded recursion. | `tail_depth > 32` degrades to `CALL; RETURN` rather than erroring, so a script cannot observe the optimisation. |
| `THROW` | Build the error value, then walk the handler cursor stack. If no handler in this frame, pop the frame and continue in the caller. | Always leaves the register file consistent for the handler's entry state: every register the handler block writes is written by `CATCH_MATCH`. |
| `ITER_NEXT` | Advance the `IterState` in `R[a]`, write the element to `R[a+1]`, set `R[a+2]`. | `IterState` is a `Value`, so a builtin iterator is a builtin object, not a Rust-side enum. This is what lets `range` be lazy. |
| `MAKE_CLOSURE` | Allocate the closure, copy upvalue descriptors, and for each open descriptor create an `Arc<Upvalue>` cell and write it into **the parent's** upvalue array. | Allocation can fail only via OOM (§4.6). Descriptor sources are staged through `spill` to survive a self-referential window. |
| `IC_CALL` | Read the cache entry at `ic[site]`, compare its shape tag, and on a hit call the cached `MethodRef` directly. | A hit is 2 loads and a compare. A miss goes to `#[cold]` `ic_miss`, which re-reads the dictionary and **re-patches the entry in place**. |
| `CLOSURE` (a Zen function) | Same as `MAKE_CLOSURE` but for a non-capturing function: a single allocation of `Closure` with `upvalues = 0`, cached in `vm.closures[proto_idx]` so a non-capturing function literal is **one** allocation ever. | The `vm.closures` table is a `Vec<Option<Closure>>` indexed by proto, so a hot function literal allocates nothing per call. This is where most of the "cheap closure allocation" in [`00-blueprint-review.md`](00-blueprint-review.md) A6 actually comes from. |

### 3.5 `unsafe` confinement

[`00-blueprint-review.md`](00-blueprint-review.md) §5.4 requires the `unsafe` surface to be a short
auditable list confined to two modules. The crate is set up to make that mechanical rather than a
matter of reviewer vigilance:

```rust
// zen-vm/src/lib.rs
#![deny(unsafe_op_in_unsafe_fn)]
#![deny(
    clippy::undocumented_unsafe_blocks,
    clippy::missing_safety_doc,
    // No unwrap / expect / direct indexing / unchecked arithmetic anywhere in
    // the crate. The hot paths that *must* index use `get_unchecked`, which
    // this lint does not touch, so the ban does not conflict with §3.2.
    clippy::unwrap_used,
    clippy::expect_used,
    clippy::indexing_slicing,
    clippy::panic,
    clippy::todo,
    clippy::unimplemented,
)]

// Module-level `unsafe` confinement, enforced at build time by a
// `build.rs` that greps for `unsafe` outside the allow-list and fails.
mod value;   // NaN-box punning only: Value <-> u64, and the 48-bit assert
mod gc;      // M9 only. Empty and `unsafe`-free in M4–M8.
```

```rust
// zen-vm/build.rs (sketch)
const UNSAFE_ALLOWLIST: &[&str] = &["src/value.rs", "src/gc.rs"];

fn main() {
    for entry in walk("src") {
        if !UNSAFE_ALLOWLIST.contains(&entry.as_str()) && entry.contains("unsafe") {
            println!("error: `unsafe` outside value.rs/gc.rs in {}", entry);
            std::process::exit(1);
        }
    }
}
```

`build.rs` grepping for a keyword is crude, and that is the point: it is a *crude, unarguable*
check that a reviewer does not have to perform. The complete `unsafe` list in M4 is **five**
functions, all in `value.rs`:

| Function | Why it needs `unsafe` |
|---|---|
| `Value::to_bits` / `from_bits` | Transmuting between the `u64` NaN-box and the structured accessors. |
| `Value::as_f64` / `from_f64` | Reading a `f64` out of the payload field. |
| `Value::from_ptr` | Building a tagged pointer, with the `debug_assert!(addr >> 48 == 0)` required by [ADR-0001](decisions/ADR-0001-tag-budget.md). |
| `registers.get_unchecked` (§3.2) | The one hot-path unchecked index. |

`git grep -n unsafe zen-vm/` returning those five lines is a **CI assertion**, and it is how the
§5.4 promise is kept honest as the crate grows.

## 4. No panics, ever

This is the longest section in the document because it is the most important one.
[`00-blueprint-review.md`](00-blueprint-review.md) §5 defines "stable" as "no input can abort the
process", and §5.4 makes the `unsafe` surface auditable. This section is the enumeration that
turns that policy into code review.

### 4.1 The old runtime's three panics, and what replaces each

`grep -n 'panic!' src/runtime.rs` finds panic sites that a script can reach. Each one is a
process abort today and a catchable `ZenError` after M4.

| Old site | How a script reaches it | Replacement |
|---|---|---|
| `src/runtime.rs:225`, inside `deref_cells` — `panic!("cyclic cell chain")` | `var x = 1; var f = lambda() { x }; f = [f]; f[0] = f; print(f())`. Any self-referential closure cycle. | **The cycle is unconstructible.** [`07-bytecode.md`](07-bytecode.md) §9.1 proves every captured cell is exactly one level deep, so `deref_cells` has no recursion and no panic branch at all. The function is deleted. |
| `panic!` from `unwrap()` in the throw path — `self.thrown_values.pop().unwrap_or(Value::Null)` at `src/runtime.rs:10582` and `10600` | Not a panic, but worse: a **silently wrong** answer. The thrown value is held in a side channel (`Vm::thrown_values`, `src/runtime.rs:3486`) and matched by a magic sentinel string (`INTERNAL_THROW_SENTINEL`, `src/runtime.rs:168-172`). If the side channel and the `Err` return get out of sync — and `exec` at `src/runtime.rs:10587-10602` re-pops at two different call sites — the user gets `unhandled exception: nullType: ` instead of their error. | **No side channel.** An error is an `Err(VmErr)` returned from `run`, and the handler cursor stack (`vm.handlers`) is the only state an unwind touches. A value cannot be "lost", because it is in the `Err`, and the sentinel string does not exist. |
| Implicit panics: slice index, integer overflow, division by zero, `Vec` growth | `d[1000000]` on a 3-element list, `a + b` at `MAX_I48`, `1/0`, an infinite `list.append` loop | §4.2 to §4.6, each with a table. |

The middle row is the one worth dwelling on. The sentinel-string design was not a panic but it had
a panic's failure mode — a process-wide invariant maintained by convention across 10 000 lines of
tree-walker, with two hand-written re-pop sites. **The lesson generalises: a thread-global side
channel is a global mutable invariant, and the M4 design keeps the number of such invariants at
zero.** `vm.handlers` is per-`Vm` and per-frame, and the only code that touches it is `try_push`,
`try_pop`, and the unwinder.

### 4.2 Illegal opcodes, and why the `match` needs a `_` arm

A `.zeno` file is data. A corrupted or hostile one can contain any of 256 `op` values, of which
**111 are defined** (104 core + 6 super + 1) and 145 are not. Two rules:

1. **The `match` has a mandatory `_ => return Err(self.bad_opcode(...))` arm.** Without it, Rust
   either emits a bounds check on the jump table or, worse, with `-C panic=abort`-style
   optimisations, indexes past the table. The arm is `#[cold]`, returns
   `ErrorKind::NativeError` with a message naming the byte and the file offset, and the loader
   *additionally* rejects such a file at load time (§11.2, test 12) so the error is reported once,
   before execution, with a proper message.
2. **The bytecode validator runs at load time, not just at compile time.** A `.zeno` built by
   Zen 3.0.0 and loaded by Zen 3.0.1 — or a hand-edited one — goes through the same
   `validate()` from [`07-bytecode.md`](07-bytecode.md) §4.2. `zen run` on a bad file is a clean
   `CompileError`-shaped message and a re-compile from source; there is no path from a bad file to
   a wrong answer.

### 4.3 Integer arithmetic in the VM

The release profile sets `overflow-checks = true` (`zen/Cargo.toml:58`, commented *"NOT off — see
docs/01-principles.md §4"*), so **an arithmetic overflow anywhere in the VM is a panic.** That is
deliberate for the *language* semantics and dangerous for the *VM's own* arithmetic, which is
mostly index math. The rule:

| Quantity | Type | How it is computed |
|---|---|---|
| Zen `int` | i48 in a 48-bit payload | **Never Rust arithmetic.** `wrapping_add` on the masked payload, then an explicit overflow test that promotes to `float`. Handled in `value.rs`, and it is the one place `i48` semantics live. |
| Register index | `u8` operand, `u16` result | `base as usize + a as usize` in `usize`, which cannot overflow because `base <= 250` and `a <= 255`. |
| `pc` | `u32` | Monotonic within a proto. A proto is limited to `u32::MAX / 4` instructions by the loader, so `pc + 1` cannot wrap. |
| Jump offsets | `i32` field | Computed as `pc as i32 ± offset`. A jump target outside the code array is a **load-time** error, so at run time the add is in range by construction. |
| Constant pool index | `u8`/`u16` | Validated `< proto.consts.len()` at load time. |
| Array/list index | `i48` | `i48 as usize` after an explicit `< 0` and `< len` check. A negative index is `IndexError`, not a wrap to a huge `usize`. |
| IC site index | `u16` | Validated at load time. |

`clippy::arithmetic_side_effects` is **not** enabled crate-wide, because it would fire on all of
the above and force `wrapping_*` noise in the value layer, where the overflow *is* the semantics.
It is enabled as `#![deny]` in the `exec.rs` module only, so index arithmetic must be explicitly
`checked_*`, `saturating_*` or `wrapping_*`. That is the right granularity: the module where an
overflow would be a wrong answer, and not the module where it is a feature.

### 4.4 Division

`DIV` and `MOD` by zero are `DivideByZero` errors, checked before the division. Two details:

- **`MOD` follows the sign of the dividend**, matching the legacy `fmod` behaviour in
  `src/runtime.rs` rather than Rust's `%`. `-7 % 3` is `-1` in Zen, and the M3 differential
  harness is what pins this down. A change here is a language change, not a VM change.
- **`INT_MIN % -1` does not exist in i48** (the range is symmetric and tiny), so the
  overflow-UB case Rust warns about cannot arise. `INT_MIN / -1` is `+2⁴⁷`, in range, and is
  computed by the masked path.

### 4.5 Stack overflow, and why it is a counter and not a guard page

[`00-blueprint-review.md`](00-blueprint-review.md) §5.3 requires stack overflow to be catchable and
detected by a depth counter. The counter is `frames.len()` against `vm.max_depth`:

```rust
#[cold]
fn exec_call(&mut self, inst: Instruction) -> VmResult<()> {
    if self.frames.len() >= self.max_depth as usize {
        return Err(self.raise(ErrorKind::StackOverflow,
            format!("call depth exceeded {}", self.max_depth)));
    }
    // …
}
```

**Why not a guard page.** A guard page (`mprotect` a page below the stack, or a sigaltstack
handler) is the standard technique and it is wrong here for two reasons. It detects *native* stack
exhaustion, and the VM's native stack use per Zen call is not bounded by anything the VM controls —
it depends on which opcode is executing. And the resulting signal is not a value; delivering it as
a catchable `ZenError` means either a `siglongjmp` out of a signal handler (formally UB-adjacent and
skips every destructor, so every `Arc` in flight leaks) or a `longjmp` through Rust frames (worse).
**A counter cannot be wrong, cannot leak, and costs one compare on a path that already does three
pushes.** The price is that `max_depth` is a policy number rather than a hardware number.

`DEFAULT_MAX_DEPTH = 8192` is chosen so that the *native* stack of an 8 MiB thread is not
exhausted before the counter fires, with ~900 B of worst-case native stack per Zen call in a debug
build **[E]**: 8192 × 900 B = 7.4 MB. In release the per-call native use is far lower, so the
counter is conservative there. This is the one place where a debug build and a release build could
behave differently, and it is handled by a test that asserts recursion to `max_depth` produces
`StackOverflow` in **both** profiles (§11.1, test 6).

### 4.6 Out of memory, and the one honest exception

Allocation failure in Rust calls `handle_alloc_error`, which aborts. It cannot be caught, and no
amount of design in the VM changes that.

**Ruling, stated plainly rather than hidden: OOM is a fatal host error, not a catchable `ZenError`.**
It is reported with a message that says so, and the process exits non-zero. This is a deliberate,
narrow deviation from §5.1's "no input can abort the process", and the justification is that
catching it would require a `try_reserve`-on-every-allocation discipline whose cost is 5–10 % on
every allocation **[E]** — a permanent tax to fix a case that is not recoverable anyway (the
allocator cannot tell you how much it needs).

What *is* done about it:

- **`try_reserve` on the two growable structures that a script can grow without bound** —
  `frames` and the global table — so the two realistic OOM paths (infinite recursion, infinite
  globals) produce a clear `OutOfMemory`-flavoured message rather than a generic abort.
- **The `len` limits in the language spec bound the rest.** A list is capped at 2³² elements, a
  string at 2³² bytes, call depth at 8192, registers at 250. Every unbounded loop must therefore
  *allocate* to exhaust memory, and the flat-RSS test ([`00-blueprint-review.md`](00-blueprint-review.md)
  §5.6) covers the "allocates and drops" case.
- **A `zen --mem-limit N` flag** installs a counting global allocator that returns a clean error
  above `N`, so the OOM path is *testable* in CI rather than only reachable by luck.

This deviation is on the §13 list for a reviewer to accept or reject explicitly. It is the only
place where this document does not deliver a catchable error.

### 4.7 The panic hook, as a last line of defence

[`00-blueprint-review.md`](00-blueprint-review.md) §5.1 requires the binary to install a hook that
converts an escaped panic into a Zen error with a non-zero exit code. It does, and it is a *net*,
not a mechanism:

```rust
// zen-bin/src/main.rs
std::panic::set_hook(Box::new(|info| {
    // Never panics, never allocates on the error path beyond a `String` that
    // is already built. Runs on whatever thread panicked.
    let msg = panic_message(info);              // &str, no allocation
    eprintln!("internal error: {msg}");
    eprintln!("this is a Zen bug; please report it at https://github.com/…/issues");
}));
```

Three rules for what the hook does **not** do: it does not print a backtrace to stdout (it would
corrupt program output), it does not re-panic, and it does not `exit(0)`. The exit code is 101,
distinct from the 1 used for a normal uncaught Zen error, so a test can tell "the script had an
error" from "the VM has a bug". A `zen test` run that reports exit 101 **fails**, even if the
script's own output matched.

`clippy::panic` is denied crate-wide (§3.5), so an explicit `panic!` cannot be introduced; what the
hook catches is an `unwrap` on a `None` that a code path did not anticipate, or an arithmetic
overflow in a module where §4.3 did not apply. It is the last line, and the first line of the
§11 test plan is designed to make sure it is never needed.

## 5. The frame model

### 5.1 The six rules of a call

`CALL` and `RETURN` are the two opcodes that must never be wrong, so their invariants are written
out rather than left in the code.

1. **Arguments are already in place.** The caller has `MOVE`d them into `R[callee_base + 0..argc]`.
   `CALL` does not marshal anything; it pushes a `Frame` with `base = callee_base` and
   `window_end = base + proto.frame_size()`.
2. **`R[0]` of a Zen function is the first parameter.** For a method, `R[0]` is `self`, because
   `compile_method` puts `self` in slot 0 in the old tree too
   (`src/bytecode.rs:241-246`) and the new compiler keeps that layout.
3. **The callee owns exactly `base..window_end`.** Every other register belongs to the caller and
   is untouched by the callee, which is what makes a tail call a memcpy instead of a copy of the
   whole file.
4. **`num_locals > 250` is impossible** — rejected by the validator (§3.2), so `window_end` fits a
   `u16` and the window check is `callee_base as u16 + frame_size as u16 <= NUM_REGS as u16`.
5. **A `Frame` is 40 bytes** (padded from the fields in §2.2). `Vec<Frame>` with
   `reserve(8192)` is 320 KiB, reserved once at `Vm::new`.
6. **A return value is a `Value` in a register, not a stack slot.** `RETURN %ra` writes
   `R[caller_base + a]`. There is nowhere else for it to go.

```rust
#[inline(always)]
fn exec_call(&mut self, inst: Instruction) -> VmResult<()> {
    let argc = inst.c as usize;
    let target = self.frame().base + u16::from(inst.a);      // callee window start
    let (proto, code) = self.resolve_call(inst.b)?;          // 07-bytecode.md §3.7

    // Rule 4. A hard error, not a debug_assert: this is the check that
    // keeps `reg()`'s `get_unchecked` sound for *nested* frames.
    let end = target
        .checked_add(proto.frame_size() as u16)
        .filter(|e| *e <= Self::NUM_REGS as u16)
        .ok_or_else(|| self.raise(ErrorKind::NativeError,
            "register window overflow".into()))?;

    self.frames.push(Frame {
        proto: proto.as_ptr(),
        code: proto.code.as_ptr(),
        base: target,
        pc: 0,
        window_end: end,
        caller_base: self.frame().base,
        return_ip: self.ip,                                   // already pc + 1
        handler_base: self.handlers.len() as u16,
        upvalue_count: 0,
        is_tail: false,
    });
    self.ip = 0;
    Ok(())
}

#[inline(always)]
fn exec_return(&mut self, inst: Instruction) -> VmResult<()> {
    let ret = self.reg_at(self.frame().caller_base, inst.a);
    let f = self.frames.pop().expect("frames is non-empty; run() guards this");
    if f.upvalue_count > 0 { self.close_upvalues(f); }        // implicit, §8 of 07-bytecode.md
    self.ip = f.return_ip;
    self.code = f.code;
    self.regs_at(f.caller_base, inst.a) = ret;
    Ok(())
}
```

`expect` appears in the example because the *real* code uses it only where the invariant is
established one line earlier in the same function; §4.7's net is for the cases where it is not. A
`#[cfg(test)]` test asserts the frame stack is empty exactly when `run` returns, so the `expect`
is unreachable by construction rather than by argument.

### 5.2 Arguments: positional, defaults, `*rest`, `**kwargs`

The compiler emits `LOAD_DEFAULT` at the top of any function with defaults, and the call site
emits `MAKE_REST` / `MAKE_KWARGS` only when the caller actually uses `*` or `**`. The VM has
exactly four cases:

| Case | Caller emits | Callee body | Cost |
|---|---|---|---|
| All positional, no defaults | `MOVE`×n, `CALL` | nothing | n moves |
| Fewer args than params, all defaulted | `MOVE`×m, `CALL` | `LOAD_DEFAULT %r{m+i}, #i` × k | k register reads |
| `*rest` present | `MAKE_REST %rt, %r_base, n, 1`, `CALL` | `MAKE_REST %rP, %r_base, P, 1` | one small `Vec` allocation |
| `**kwargs` present | `MAKE_KWARGS %rk, %r_base, n, 1`, `CALL_KW` | `MAKE_KWARGS %rK, %r_base, P, 1` | one small `Vec` + one `Dict` allocation |

`MAKE_REST` and `MAKE_KWARGS` are **the only two opcodes that allocate in the common path**, and
only for functions that use `*`/`**`. `MAKE_REST` builds a `Vec` by copying `R[base..base+n]`, so
the callee's `rest` is independent of the caller's registers — which is required, because the
caller's registers are clobbered by the next call.

`LOAD_DEFAULT` reads `proto.defaults[i]`, the `Vec<Value>` the module-load hook filled from the
defaults thunk ([`07-bytecode.md`](07-bytecode.md) §10.4). **The VM never evaluates a default
expression.** A default is either a constant in the pool or a value computed once at module load;
there is no third possibility, and no opcode that could evaluate one. This is what makes the cache
in [`07-bytecode.md`](07-bytecode.md) §10.4 possible at all.

**Arity errors.** A call with too many arguments, or too few with an unfilled parameter, is
`ArgumentCount` at **run time**, not compile time — because `f(*args)` makes the count dynamic. The
message names the function, the expected range (`"expected 1 to 3 arguments, got 5"`), and the
span, and it is catchable:

```
$ zenn run t.z
error: ArgumentCount: greet() expected 1 to 3 arguments, got 5
   3 | greet("a", "b", "c", "d", "e")
     |               ^^^^^^^^^
```

### 5.3 Tail calls

`TAIL_CALL` exists so `return f(x)` in a recursive function is a loop, not unbounded recursion. It
reuses the current frame:

```rust
fn exec_tail_call(&mut self, inst: Instruction) -> VmResult<()> {
    // Bounded: past 32 reuse levels, degrade to CALL;RETURN rather than
    // growing the native stack. A script cannot observe the difference.
    if self.frame().tail_depth >= 32 {
        self.exec_call(Instruction { op: Op::CALL.into(), a: inst.a, b: inst.b, c: inst.c })?;
        self.exec_return(Instruction { op: Op::RETURN.into(), a: inst.a, b: 0, c: 0 })?;
        return Ok(());
    }
    // Move the new callee's window down over this frame's window, then
    // rewrite the frame header in place. `caller_base`/`return_ip` are
    // preserved, so the eventual RETURN goes to *our* caller.
    let f = self.frames.last_mut().expect("non-empty");
    let new_base = f.base + u16::from(inst.a);
    // … copy proto, code, window_end, bump tail_depth …
}
```

The argument copy is a `memcpy` of at most 250 `Value`s, and in the common case of 0–3 arguments it
is 3 `Value` moves. **The M4 measurement to make this ruling real is `bench_recursion`**: a tail-call
chain of depth 10⁷ must not grow the frame stack, and must not grow RSS. If the profile shows
`exec_tail_call`'s bookkeeping costing more than the `CALL; RETURN` it replaced, the ruling flips
and the opcode becomes a no-op — that is what `tail_depth` and the degradation path are for.

### 5.4 Unwinding: one `Err`, one cursor stack

An error is an `Err(VmErr)` out of `run`, and the unwinder is a loop over `vm.handlers`:

```rust
/// Find a handler for `err` in the current frame, or pop the frame and
/// try the caller. Returns the pc to resume at.
fn unwind(&mut self, err: &VmErr) -> Option<(usize, HandlerCursor)> {
    while let Some(f) = self.frames.last() {
        if let Some(h) = self.find_handler(f, err) {
            return Some((self.handler_entry_pc(h), *h));
        }
        // No handler here. Close this frame's upvalues — they may be
        // captured by a closure that outlives the frame — and pop.
        if f.upvalue_count > 0 { self.close_upvalues(*f); }
        self.handlers.truncate(f.handler_base as usize);
        self.frames.pop();
    }
    None
}
```

Four properties, each of which the old sentinel-string design did not have:

1. **The thrown value is in the `Err`**, so it cannot be lost by a mismatched pop.
2. **Closing upvalues on the way out** is required for correctness, not tidiness: a closure that
   captured a local of the frame being unwound must see a `Closed` cell, or the cell would hold a
   dangling `ParentLocal` register index that the next frame now owns. This is a **use-after-free
   class bug that the old tree does not have and the new one must**, which is why
   `close_upvalues` is called from `exec_return` *and* from `unwind` *and* from the `RETURN_UNIT`
   path — three call sites, all listed in [`07-bytecode.md`](07-bytecode.md) §9.4.
3. **`finally` runs on both paths.** If a frame has a finally handler and no matching catch, the
   unwinder rewinds to the finally's `finally_end` and re-raises with `RERAISE`. The old
   tree-walker tracks this with a `prev_flow: Flow` chain in `exec`
   (`src/runtime.rs:10587-10602`), which is correct but requires every one of ~200 `exec_one` arms
   to propagate `Flow` by hand; the exception table makes it a property of the table instead of a
   convention in 200 places.
4. **A re-raise is not a Rust re-panic.** `RERAISE` re-enters `unwind` with the *same* `VmErr`, so
   `err` is never cloned and never re-boxed. A traceback is captured once, at the `THROW` site, and
   carried in the `VmErr`.

## 6. Inline caches

**M5, designed in now.** [`00-blueprint-review.md`](00-blueprint-review.md) A6 calls inline caching
"the single biggest win in every real VM" and "roughly a day's work". The design constraint is that
the VM's data structures in §2.1 must already accommodate them, because a cache is a *side table
indexed by an operand of an instruction*, and if the instruction's operand is a `u8` register
number then the site needs a home. It does: `IcSite` records, emitted by the compiler, assigned
dense indices in `pc` order per proto, and `vm.ic` is the flat concatenation in the same order.

### 6.1 The cache entry

```rust
/// One cache slot. 8 bytes, 4 to a cache line, no pointers, no atomics.
#[repr(C, align(8))]
#[derive(Clone, Copy)]
pub struct InlineCache {
    /// The `ShapeId` this entry is specialised for, or a `Type` tag for
    /// `IC_CALL`, or one of the sentinels below.
    guard: u32,
    /// On a hit: the field's slot index (GET/SET), or an index into
    /// `vm.methods` (CALL). Never a pointer, so the JIT can emit it as an
    /// immediate and the interpreter never chases it during the guard.
    action: u32,
}

pub const IC_EMPTY: u32        = 0;      // never specialised
pub const IC_MEGAMORPHIC: u32   = u32::MAX; // gave up; always take the slow path
/// Bit 31 set: this entry is polymorphic and `action` is an index into
/// `vm.ic_poly[entry]`, a small `Vec<(u32, u32)>`.
pub const IC_POLY_FLAG: u32     = 0x8000_0000;
```

`guard` is a **`ShapeId` (an index), not a pointer**. That choice is what makes an inline cache
invalidation-free: shapes are append-only (§7.1), so a `ShapeId` is never reused for a different
layout. A stale entry compares unequal and misses. There is no generation counter, no write
barrier, and no global invalidation pass — and therefore **no atomics and no lock on the hot
path**.

**The hit path is one branch on the entry's own guard**, and the polymorphism check is a bit test
on the same load, so a monomorphic hit and a polymorphic hit share the fetch:

```rust
#[inline(always)]
fn ic_lookup(&self, site: u32) -> Option<u32> {
    let e = self.ic[site as usize];
    let g = e.guard;
    if g & IC_POLY_FLAG == 0 {                    // monomorphic or megamorphic
        // The caller already compared `g` against the receiver's shape;
        // this is the same compare, folded by LLVM.
        return if g == IC_MEGAMORPHIC { None } else { Some(e.action) };
    }
    // Polymorphic: 2 compares, unrolled, no loop. 2 is the cap (§6.3), so
    // this is a fixed-size scan the compiler can keep in registers.
    let pair = &self.ic_poly[(g & !IC_POLY_FLAG) as usize];
    if pair[0].guard == CURRENT { return Some(pair[0].action); }
    if pair[1].guard == CURRENT { return Some(pair[1].action); }
    None
}
```

### 6.2 Which opcodes carry a site

| Opcode | `guard` is | `action` is | Hit cost |
|---|---|---|---|
| `IC_GET_FIELD %rd, #site, $N"name"` | `ShapeId` of the receiver | slot index | `cmp` + `mov` = 2 instructions |
| `IC_SET_FIELD %rs, #site, $N"name"` | `ShapeId` of the receiver | slot index | `cmp` + `mov` |
| `IC_GET_INDEX %rd, #site, %rk` | `ShapeId` of the receiver | slot index | `cmp` + `mov` |
| `IC_SET_INDEX %rs, #site, %rk` | `ShapeId` of the receiver | slot index | `cmp` + `mov` |
| `IC_CALL %rd, #site, n` | `Type` of the callee (or `ShapeId` for a method lookup) | `MethodId` into `vm.methods` | `cmp` + indirect call |
| `IC_INC %rd, #site, delta` | `ShapeId` | slot index | fused get-add-put on a numeric field |
| `PUSH_HANDLER #site, size` | — | `HandlerId` | not a cache; see §6.7 |

`IC_INC` is the one that pays for itself fastest. `self.count += 1` inside a hot method is
otherwise a `IC_GET_FIELD`, a `LOAD_SMALL_INT`, an `ADD`, and an `IC_SET_FIELD` — four dispatches
and four potential cache lines. `IC_INC` is one dispatch and one cache line touched. It is the
`List.len` → `BUMP_LIST_LEN` fusion of the old VM (`src/bytecode.rs`, the `BumpListLen` variant)
generalised to object fields, and it is a **type-specialised** instruction, which is why the JIT
in M11 also wants it.

**The compiler only emits an `IC_*` when the site is a shape-stable access**, decided statically:

- `d.a` where `d` is a known dict/object → `IC_GET_FIELD`.
- `d[k]` where `k` is a *constant* → `IC_GET_FIELD` with the same site, because a constant key
  identifies a fixed slot.
- `d[k]` where `k` is dynamic → plain `GET_INDEX` with **no site**. A dynamic key has no shape to
  guard on, and a cache entry that misses every time is a pure loss: a compare plus a cold-path
  jump, in exchange for nothing.
- `x.f()` where `x` is dynamic → `IC_CALL` guarded on the *type* of `x` (a method-table index, not a
  shape), because method resolution is stable per type even when the receiver's fields are not.

### 6.3 Miss, bump, and the megamorphic decision

A miss is always a `#[cold]` function that does the slow, hash-based lookup and then **re-patches
the entry**:

```rust
#[cold]
fn ic_miss(&mut self, inst: Instruction, site: u32) -> VmResult<()> {
    let entry = &mut self.ic[site as usize];

    // Already polymorphic: append if room, otherwise the slow path.
    if entry.guard & IC_POLY_FLAG != 0 { return self.ic_slow(inst, site); }
    if entry.guard == IC_MEGAMORPHIC   { return self.ic_slow(inst, site); }

    let (real_guard, real_action) = self.lookup_shape_and_slot(inst)?;
    let polies = entry.guard & IC_POLY_FLAG != 0;
    let poly_slot = entry.guard & !IC_POLY_FLAG;

    match (polies, poly_slot) {
        // Not yet polymorphic. A miss on an unpatched or monomorphic site
        // promotes it to a 2-entry polymorphic site, keeping the old
        // guard/action as entry 0 so the previously-hot shape is still fast.
        (false, _) => {
            let old = *entry;
            *entry = InlineCache {
                guard: IC_POLY_FLAG | self.ic_poly.len() as u32,
                action: 0,
            };
            self.ic_poly.push([old, InlineCache { guard: real_guard, action: real_action }]);
        }
        // Polymorphic, and there is room for a third distinct shape.
        (true, i) if self.ic_poly[i as usize].iter().all(|e| e.guard != real_guard) => {
            self.ic_poly[i as usize]
                .push(InlineCache { guard: real_guard, action: real_action });
        }
        // Third distinct shape, or a slot whose action moved: **give up**,
        // permanently, for this site.
        (true, i) => { self.ic_poly[i as usize].fill(MEGAMORPHIC_ENTRY); }
    }
    self.ic_execute(inst, real_action)
}
```

**The policy, and the reasoning behind the numbers.** Monomorphic → 2-entry polymorphic →
megamorphic, and the third distinct shape is where it stops. Those thresholds are not arbitrary:

- A site seeing 2 shapes is a monomorphic site that got unlucky, or a genuine bimorphic dispatch
  (an `if` that picks between two classes). 2 entries covers it exactly, with a linear scan of 2
  compares — cheaper than a hash lookup, so still a win.
- A site seeing 3+ shapes in a *hot loop* is a **megamorphic site**, which
  [`00-blueprint-review.md`](00-blueprint-review.md) A6 names as the thing to avoid. Continuing to
  patch it would grow the entry unboundedly and turn a 2-compare hit into a 10-compare scan, plus
  the cache line would no longer fit in 8 bytes.
- The `IC_MEGAMORPHIC` sentinel is a **permanent, per-site decision**, not a temporary state, so the
  site costs exactly one extra compare forever. That is the correct trade: the alternative —
  re-checking whether it has become monomorphic again — is a heuristic with no sound basis.

**The honest cost of a megamorphic site.** `ic_slow` is the *same* hash lookup the non-cached
`GET_FIELD` would have done, plus one `cmp` and one predicted-not-taken branch. So a megamorphic
site is **1–2 % slower than having no IC at all [E]**, never materially slower. That asymmetry is
the whole design: ICs are free when they work, and nearly free when they do not. A design where a
failed IC was expensive — say, requiring a shape-trie walk — would be unusable on dict-heavy code,
which is most real Zen code.

**What actually makes sites megamorphic**, in rough order of frequency in real programs:
`(1)` a function that takes a dict argument and is called with many different dict shapes;
`(2)` a `Dict` used as a record bag with dynamic keys, where the *object* shape is stable but the
*access* is dynamic — this is handled by the `GET_INDEX` no-site rule in §6.2, so it never even
creates a site; `(3)` `values.map(v => v.name)` over a list of instances of several classes;
`(4)` a field genuinely written with different key types. Case (3) is the one to design around,
and the answer is the guard in §6.7.

### 6.4 Per-thread caches, and why that is free

`vm.ic` is per-`Vm`, and a `Vm` is per-thread and `!Send` (§2.5). So a cache entry can never be
torn, needs no atomic, and needs no lock: the hot path is a plain `u32` load and compare. A closure
shared across two threads gets two independent caches that each warm up on their own access
pattern — which is *better* than sharing one cache, because each thread's monomorphic guess is
fitted to what that thread actually runs.

The consequence for M10: **`Arc<Mutex<ZenObject>>` in a shared binding makes every field access on
it monomorphic-per-thread, and the lock is the mutex, not the cache.** There is no cache-coherence
problem to solve, which is a real simplification of the M10 design.

### 6.5 Invalidating: nothing to do

Because `ShapeId`s are append-only indices (§7.1) and a dictionary's shape changes only by
*transitioning* to a new id, **an inline cache entry cannot become stale-but-matching**. The only
two things that can happen to a `(site, guard)` pair are:

- the shape id still matches → the layout is the same → the cached slot is correct; or
- it does not match → miss.

A field's *value* can change without invalidating anything, because the cache stores a slot index,
not a value. `d.a = 5; d.a = 6; print(d.a)` is one compare and one load each time, and is always
correct. This is the property that makes the design robust; the equivalent design that caches
*values* needs a write barrier per assignment, which is the cost the JIT pays in V8 and the cost
this design does not.

### 6.6 The M11 handoff

The JIT needs three things from this design, and all three are why the entry has no pointers:

1. **A guard is an immediate.** `cmp dword [rip + site], shape_id; jne deopt` — the shape id is a
   compile-time constant in the emitted code, so the guard is 2 instructions and needs no VM
   support at run time.
2. **A deopt on a guard failure** re-enters the interpreter at the *same* `pc` with the same
   registers, and the interpreter's `IC_*` arm takes its miss path. This is only correct because
   **IC miss is idempotent** — it re-does the lookup and gets the same answer. If `ic_miss` had a
   side effect before re-patching, deopt would double it.
3. **Patching a deopt into a site at M5 time is possible but not done.** The M11 translator reads
   `vm.ic[site]` once when it compiles the site and bakes the guard in. It does not write back, so
   `vm.ic` stays the interpreter's, and the interpreter and the JIT never fight over an entry.

### 6.7 `PUSH_HANDLER` is not a cache, and the iterator protocol's hidden cost

`PUSH_HANDLER #site, size` appears in the table with a site operand, and it is worth being explicit
about why: the handler table is a *per-proto* array indexed by a `u16` in the instruction, and the
site operand is the index. There is no guard, no action, and no cache — the entry is constant after
load time. The opcode exists so that entering a `try` is **one dispatch and one `Vec` push**, not a
loop over the exception table to find the innermost entry covering `pc`.

**The hidden cost of the hidden iterator protocol.** [`07-bytecode.md`](07-bytecode.md) §7.2 hides a
two-register state machine in `ITER_INIT`/`ITER_DONE`/`ITER_NEXT`, so `for` costs no opcode beyond
the ones a manual loop would use. The cost is on the *state*: `IterState` is a heap object, so
every loop over a lazy iterable allocates one. For `for x in [1,2,3]` that is a small `Vec` plus an
`IterState` per loop entry — 2 allocations to run 3 iterations. §12.3 measures this
(`bench_iteration`) and the mitigation, if it shows up, is a **per-frame 1-slot inline state cache**:
if the previous iterator in this frame has been dropped, reuse its allocation. That is a real
optimisation with a real cost (a liveness check on every `ITER_NEXT`), and it is explicitly *not*
in M4.

## 7. Hidden classes and shapes

**M5.** [`00-blueprint-review.md`](00-blueprint-review.md) A6 ranks "inline caches + hidden
classes" as the second biggest speed win and the whole of M5. §6 is the cache; this is what it
caches *against*.

### 7.1 The shape, and the append-only rule

A **shape** is the layout of an object's named slots. It is interned, append-only, and identified
by its index in `vm.shapes`.

```rust
/// The layout of an object's named slots. Append-only: a `ShapeId` is never
/// reused, never mutated, and never reordered. This single rule is what
/// makes inline caches (§6) free of invalidation.
#[derive(Clone)]
pub struct Shape {
    /// How slots are stored once `len` exceeds `INLINE_SLOTS`.
    layout: ShapeLayout,
    /// Slot count. Small shapes keep their table inline; large ones point
    /// into `vm.shape_slots`.
    len: u16,
    /// For the inline case: `(name_id, slot)` pairs, in insertion order.
    slots: Box<[(u32, u16)]>,
}

#[derive(Clone, Copy, PartialEq)]
pub enum ShapeLayout {
    /// ≤ 8 fields. The table is in the Shape; a lookup is a linear scan of
    /// ≤ 8 `u32`s, which is 1–2 cache lines and beats a hash for small n.
    Inline,
    /// ≤ 64 fields. The table is in a side allocation; still linear scan.
    Side,
    /// > 64 fields, or an object written with dynamic keys. **No shape at
    /// all**: the object carries `ShapeId(0)` meaning "unshaped", and every
    /// access is a hash lookup. This is the escape hatch, and it is what
    /// makes the design total — a dict with 10⁵ keys still works.
    Unshaped,
}
```

**The append-only rule is the load-bearing decision.** Because a `ShapeId` is an index that is
never recycled:

- a cached slot index for shape *S* is correct for every object that has shape *S*, forever;
- an object that gains a field transitions to a *new* shape, so old cache entries simply stop
  matching, and they never match the *wrong* layout;
- there is no deletion, no reordering, and therefore no write barrier, no generation counter, and
  no need to walk objects on resize.

The cost is that shapes are never freed. In a program that builds millions of distinct shapes —
e.g. `for i in range(10**7) { d = {i: i} }` — `vm.shapes` grows by one `Shape` per iteration,
because each `d` transitions `{}` → `{0}`, `{1}`, `{2}`, … and each is a *different* shape. That is
a genuine unbounded-growth path and it is handled, not ignored:

> **Ruling: a shape is only interned if it is *shared*.** `vm.shape_transitions` is keyed by
> `(parent_shape, name_id)`, so `{}` → `{0}` happens **once**, ever, globally. The 10⁷-iteration
> loop above reuses the same two shapes. A loop that genuinely creates a new shape at every
> iteration — `{i: i, i+1: i}` style — would grow the table, and `zen --mem-limit` plus the flat-RSS
> test ([`00-blueprint-review.md`](00-blueprint-review.md) §5.6) is what catches it. A shape-cache
> eviction policy is **not** in M5 and is on the §13 list as the most likely M5 follow-up.

### 7.2 Objects that have shapes

| Zen type | Has a shape? | Why / why not |
|---|---|---|
| `#{a: 1, b: 2}` — dict literal | **yes**, if all keys are constant string literals | The literal's keys are known at compile time, so the shape is a constant in the pool. A dict literal with dynamic keys is `Unshaped`. |
| `d[k] = v` on a shaped dict | **yes**, via a transition | This is the point of transitions: growing a record-shaped dict keeps it shaped. |
| `class C { }` instance | **yes**, starting from the class's field-declaration shape | The class's declared fields give a starting shape, so instances of one class are monomorphic from allocation. `__init__` assigning fields in a different order transitions, and the order stabilises after the first two instances. |
| `dict` with dynamic keys throughout | no — `Unshaped` | Honest answer: a general hash map has no stable layout. |
| `list`, `string`, `int` | no | No named slots. |
| a `handle` to a native object | no | The pointee's layout is not Zen's. Field access goes through a FFI accessor. |

**The instance case is the one that needs the most care, and the rule is order-stability.** Zen
classes declare fields, so `Shape` for `class Point { x; y }` is created at class-definition time as
`{x:0, y:1}` and *every* `Point` starts from it. Then `__init__` does `self.x = x; self.y = y` —
both slots already exist, so **no transition happens at all** and every `Point` is monomorphic at
allocation. A class that assigns fields *not* declared in the class body transitions once per
distinct assignment order, and after two instances the shape converges. That convergence is a
property to be asserted in a test (§11.3, test 19), not assumed.

### 7.3 Lookup, on the miss path

The hit path is a slot index and a load (§6.2). The miss path is where a hash would be needed, and
it is where the honest costs live:

```rust
#[cold]
fn shape_find_slot(shape: ShapeId, name_id: u32) -> Option<u16> {
    let s = &self.shapes[shape as usize];
    match s.layout {
        ShapeLayout::Unshaped => None,          // caller falls back to a hash
        // Linear scan. For n ≤ 8 this is 1–2 cache lines and 1–8 compares;
        // a hash lookup is 1 random cache line plus a modulo. Measured in
        // §12.3 as part of `bench_dict`; the crossover is around n = 12.
        _ => s.slots.iter().find(|(n, _)| *n == name_id).map(|(_, o)| *o),
    }
}
```

A linear scan instead of a hash for small shapes is a deliberate choice with a measured basis: for
*n* ≤ 8, a scan touches the same 1–2 cache lines every time (they are already hot from the shape
pointer chase), while a hash touches a line determined by the hash value, which is a guaranteed
cache miss on first touch. The crossover is somewhere around *n* = 12 **[E]**; `bench_dict` with
dictionaries of 4, 16, 64 and 1024 entries is in §12.3 specifically to find it, and if the profile
disagrees the fix is a 4-entry SIMD compare over the name ids, not a hash.

### 7.4 Transition, on the write path

```rust
#[cold]
fn shape_transition(&mut self, shape: ShapeId, name_id: u32) -> VmResult<ShapeId> {
    if let Some(next) = self.shape_transitions.get(&(shape, name_id)) {
        return Ok(*next);
    }
    let s = &self.shapes[shape as usize];
    if s.len as usize >= MAX_SHAPE_FIELDS {         // 64
        return Ok(UNSHAPED);                        // total escape hatch
    }
    // Copy-on-grow: the parent shape is never mutated, so every object
    // already holding it keeps a valid layout. 1 small allocation.
    let mut next = s.clone();
    next.slots.push((name_id, next.len));
    next.len += 1;
    if next.len > ShapeLayout::Inline as usize * 8 { next.layout = ShapeLayout::Side; }
    let id = self.intern_shape(next);
    self.shape_transitions.insert((shape, name_id), id);
    Ok(id)
}
```

Note the `shape_transitions` **cache** in front of the interning: it is a hash map, so the *first*
transition for a given `(parent, name)` costs a map insert, and every later one is a map lookup. A
transition is only ever taken on a write to a *new* key, so this is off the read path entirely, and
on the write path a hash map lookup is nothing next to the dictionary write that follows it.

### 7.5 The interaction with `Arc` and copy-on-write, which is the sharp edge

[ADR-0002](decisions/ADR-0002-memory-model.md) rules that mutable state is `Arc<Mutex<Value>>` with
copy-on-write on write, and that this stays until at most M8. **CoW and shapes are in direct
tension**, and this is the most important thing to get right in M5:

- `d = #{a: 1}`; `d2 = d`; `d.b = 2`. Under CoW, `d2` is a *clone*, so `d2`'s shape is a **new**
  shape (`{a,b}`) and `d`'s is unchanged (`{a}`). Correct, and both stay monomorphic.
- But `d.b = 2` when `b` is **new** mutates `d`'s shape via a transition. If any *other* object
  shares `d` under CoW, that other object must keep the old shape — and it does, because shapes are
  never mutated (§7.1) and the object carries its own `ShapeId`. **The immutability of shapes is
  what makes CoW safe for field access.** Sharing a shape is fine because a shape describes a
  layout, and the layouts only ever diverge by creating new shapes.
- The cost: **one `Shape` allocation per distinct object shape**, amortised across all objects that
  reach it. For a program with 10⁴ objects of 4 shapes, that is 4 allocations, not 10⁴. This is the
  single most important property of the design and it is why shapes are interned globally rather
  than per-object.

The case that would break it is a program that creates a genuinely new shape per object
(`{f"{i}": i}`), which is 1 shape + 1 slot-table allocation per iteration. The `Unshaped` escape
hatch and `--mem-limit` are the mitigations; the flat-RSS test is the check.

### 7.6 Interaction with the M9 GC

M9's tracing collector needs to find the `Value`s inside an object. With a shape, the collector
scans the shape's slot table and visits exactly those slots — **no `Value` header scan, no
conservative marking.** That is a real GC win over the alternative, and it is the strongest
argument for shapes surviving into M9. The cost is that the collector must know the difference
between a shaped object and an `Unshaped` one, which is one tag compare. Recorded here so M9 is
not surprised.

## 8. The native call ABI

### 8.1 Two ABIs, and why the first one is not enough

```rust
/// **v1 — the fast path.** Arguments are borrowed straight out of the
/// callee's register window. No allocation, no copy, no `Vec`.
pub type NativeFn = fn(&mut Vm, &[Value]) -> VmResult<Value>;

/// **v2 — the staging path.** For variadic builtins and anything that
/// needs to mutate its arguments in place.
pub type NativeFnV2 = fn(&mut Vm, &mut [Value]) -> VmResult<Value>;
```

A `NativeFn` receives `&[Value]` pointing **directly into `vm.registers`**. `print("x")` is a
native call whose argument slice is a contiguous run of 1 `Value` in the register file. There is no
marshalling, no `Vec`, no clone, and the slice is `&'a [Value]` because the registers outlive the
call. This is the single most valuable property of the v1 ABI: **a builtin that only reads its
arguments cannot allocate**, and most of them do not.

The v2 ABI exists for `*args`/`**kwargs` builtins, `sort` (needs to mutate), and anything that
needs to grow a slice. It writes into `vm.native_args`, which is reserved once at `Vm::new`.

```rust
/// How a native is stored. A `NativeEntry` is 24 bytes: a tag, a fn
/// pointer, and a name id.
#[derive(Clone, Copy)]
pub struct NativeEntry {
    /// Arity check the VM does before the call. `ARITY_VARIADIC` skips it.
    arity: Arity,
    /// The v1 or v2 function, discriminated by `is_v2`.
    f: NativeFn,
    /// Zen-visible name, for `NameError: print is not a function`.
    name_id: u32,
    is_v2: bool,
}
```

### 8.2 The buffer-copying problem, and the `Arc` answer

The awkward part of a native ABI is ownership. A `NativeFn` gets a borrow, so it cannot store a
pointer to the argument. If a builtin needs to keep a value beyond the call it must clone it, and
cloning a `string` is a `memcpy` of its whole contents.

**Ruling: `string` and `bytes` are `Arc`-backed, not inline.** So a clone is an atomic increment,
not a copy, and the v1 ABI's borrow is not a lifetime problem for the common case.

```rust
/// NaN-boxed, 8 bytes, tag in bits 48..51 (ADR-0001). The struct form is
/// only for the `Debug` impl and the `unsafe` accessors; the interpreter
/// only ever touches the `u64`.
pub enum ValueRepr {
    /// tag 0b000: nil
    Nil,
    /// tag 0b001: false
    False,
    /// tag 0b010: true
    True,
    /// tag 0b011: i48 in the low 48 bits, two's complement
    Int(i64),
    /// tag 0b100: raw f64 bit pattern (exponent != all-1s)
    Float(f64),
    /// tag 0b101: `Arc<str>` pointer. Cloning is an atomic increment.
    Str(Arc<str>),
    /// tag 0b110: `Arc<[u8]>` — `bytes`
    Bytes(Arc<[u8]>),
    /// tag 0b111: heap object — discriminated by `ObjHeader.kind`
    Heap(ObjRef),
}
```

**ObjRef** is a tagged `NonNull<ObjHeader>` with a manual refcount, not an `Arc<ObjHeader>`.

The `shape` field in the header is what makes §7's hit path a single load: `guard` comparison
against `obj.shape`, then `obj + offset[shape.slots[k]]`. Both in the same cache line as the
object's first slots.

### 8.3 `&mut Vm` as the second argument, and why it is not `&mut Runtime`

Every native takes `&mut Vm`. That is the whole context it needs: the register file (to call back
into Zen), the natives table, the string interner, the shapes, the IC table, and the error
machinery. The legacy runtime's alternative — passing `&mut Runtime` implicitly through a
thread-local — is what produced `INTERNAL_THROW_SENTINEL` and the `thrown_values` side channel
(§4.1). **Passing the context explicitly is the structural fix**: a native that wants to call a Zen
function has a `&mut Vm` in hand, so it cannot reach for a global.

One consequence worth flagging: a native holding `&mut Vm` across a Zen call has an aliasing
problem, since the Zen call will push frames into `vm.frames` and can move the registers it was
borrowing. The rule is that `exec_call` **re-reads the callee window pointer after the callee
returns**, and no native may hold a `&Value` into the register file across a `CALL`. This is stated
in `unsafe`-free terms because the register slice handed to a native is a reborrow, and the
lifetime ends at the native's return.

## 9. C-level entry points for the JIT

**M11, but the ABI is frozen in M4.** The single most expensive mistake available in a JIT project
is to design the VM, then discover the JIT needs a different interface. So the interface is
specified now, and `zen-vm` implements the M4 side of it in M4 as two `#[no_mangle] extern "C"`
functions with empty bodies on non-JIT builds.

### 9.1 The two functions

```rust
/// Compile `proto` to machine code. Returns an opaque handle. Called from
/// the background JIT thread; **must not** touch `vm` — it is passed
/// `&FunctionProto` and the code array only, both immutable.
/// # Safety
/// `proto` must outlive the returned handle.
#[no_mangle]
pub unsafe extern "C" fn zen_jit_compile(
    proto: *const FunctionProto,
    ic_sites: *const IcSite,
    ic_len: usize,
    out: *mut JitHandle,
) -> i32;

/// Execute compiled code. Called on the **owning** thread only, re-entrantly
/// from the interpreter's frame.
/// # Safety
/// `handle` must have been produced by `zen_jit_compile` for a proto whose
/// frame_size and ic layout match the current `vm`.
#[no_mangle]
pub unsafe extern "C" fn zen_jit_execute(
    handle: *const JitHandle,
    vm: *mut Vm,
    base: u16,
) -> i32;
```

`zen_jit_execute` is re-entrant because the JIT's machine code **calls back into the interpreter**
for three things: an IC guard failure (deopt), a call to a function that is not yet compiled
(interpreter entry), and any operation the translator decided not to lower. Each of those is a
call into `exec`'s arm for that opcode, with the same registers, so a deopt is exact by
construction.

### 9.2 The frame descriptor, and the one thing that must not change

For M9's collector and for the JIT's stack maps, every frame needs a machine-readable description
of which registers are live:

```rust
/// What the collector and the JIT need to know about a frame.
pub struct FrameDescriptor {
    /// Registers 0..frame_size are the frame. Roots for the GC.
    frame_size: u16,
    /// Bit i set: register base+i holds a `Value` that may be a heap
    /// pointer. The GC scans exactly these. For a straight-line-compiled
    /// proto this is every register up to the high-water mark, which is
    /// why the register discipline ([`07-bytecode.md`](07-bytecode.md) §6.2)
    /// was chosen for simplicity: **conservative-but-tight is acceptable,
    /// conservative-and-unbounded is not.**
    live_regs: u64,          // 4 words; 256 registers
    /// Upvalue array length, for the closure's cells.
    upvalue_count: u8,
    /// Index of the first IC site in this proto, and the count. The JIT
    /// reads `vm.ic[ic_base..ic_base+ic_len]` to bake guards.
    ic_base: u32,
    ic_len: u16,
}
```

`live_regs` as four `u64`s covers all 256 registers, so **the bitmap is fixed-size and
frame-descriptor size does not depend on `frame_size`.** That is the decision that lets the JIT's
metadata be a constant-size table.

### 9.3 What the JIT needs from the bytecode that is not in an `Instruction`

Three things, all of which must therefore be in the `.zeno` file (and all of which exist in
[`07-bytecode.md`](07-bytecode.md) already or must be added there):

1. **The span/line table**, for a deopt that has to produce a source location.
2. **The IC site table**, for the guards (§6.6). `SECT_IC_SITES` exists; `HAS_IC_SITES` is the flag.
3. **The exception table**, so the translator knows where it may need to materialise a landing pad
   rather than re-entering the interpreter.

### 9.4 The deopt contract, in one paragraph

A deopt is **"re-enter the interpreter at the same `pc` with the same register file."** That is the
*only* deopt kind. There is no "reconstruct state from a debug info blob" and no
"re-execute from the loop header" — both are how JIT deoptimisation turns into a bug farm. The
translator emits, for every site it cannot handle, a `deopt(target_pc)` call into the interpreter;
because the interpreter's semantics for that `pc` are the reference semantics, a deopt is always
correct, and the only thing it can be *wrong about* is a register the JIT clobbered — which the
`live_regs` bitmap in §9.2 prevents by requiring spill slots to be written back before any
`deopt`.

## 10. The REPL and inspector interface

M8, but it constrains M4's `Frame` layout, so it is specified now. The REPL is not a nice-to-have:
it is the primary debugging tool, and a VM that cannot be stepped is a VM whose bugs are found by
`println!`.

### 10.1 Three levels of introspection

| Level | API | Used by |
|---|---|---|
| **Step** | `vm.set_step(n)`, `vm.run()` returning after *n* instructions | `zenn repl` (Ctrl-C to interrupt), `zen test --step` |
| **Frames** | `vm.frames()` → `&[FrameInfo]` with proto name, function name, source line, and live register count | the `>>> bt` backtrace |
| **Inspect** | `vm.inspect(reg)` → a `&[Value]` view, and `vm.frame_locals(frame)` | the `>>> locals` command, and the test harness's assertion diffs |

All three are `#[cfg(any(debug_assertions, feature = "zen-debug"))]`-gated behind a
`DebugPause` enum whose only non-`Off` values are behind that gate, so a release build has the
`if` and not the machinery.

### 10.2 The step budget is a counter, not a signal

Ctrl-C in a runaway loop must not corrupt the VM. Two designs:

- A signal handler that sets an `AtomicBool` — unsafe to do anything more, and
  `step_budget` as a plain `u64` read in the dispatch loop's top is **one decrement of a
  register-resident value** on an already-hot path, so it is free enough to leave in.
- A separate thread poking the VM — impossible, `Vm` is `!Send` (§2.5).

**Ruling: the `AtomicBool` is set by the signal handler; the dispatch loop copies it into
`step_budget` once every 4096 instructions**, so the atomic load is off the per-instruction path
entirely. The 4096-instruction latency is imperceptible (< 10 µs) and the cost is a predictable
branch that the branch predictor gets right every time.

The step budget is also what makes `zen test --step` possible: it makes the VM's execution order
*deterministic and observable*, which is the precondition for the §11.4 fuzzing differential.

### 10.3 The REPL is not a special mode

The REPL is a `Vm` with `debug_pause` set, a `step_budget`, and a `globals` table that persists
between lines. Each line is: parse → compile (fresh, from the same compiler as a file) → execute in
the **same** `Vm`, so `let x = 1` on line 1 is visible on line 2 because it went into
`vm.globals`. There is no separate "REPL interpreter", no AST-node cache, and no mode flag in the
dispatch loop.

**The one thing that is REPL-specific is uncaught-error reporting**, and this is where the design is
subtler than it looks. A top-level error in a file prints a source-located message and exits 1. The
same error in the REPL prints the message and then has to decide what state to leave behind, because
half-applied top-level statements (`x = 1; y = undefined; z = 3`) leave `x` assigned and `z` not.

| Candidate | Cost | What it actually restores |
|---|---|---|
| **Snapshot the globals table** (copy the `Vec<Value>` before the line, restore on error) | ~1 µs for 64 globals — invisible | Only the **bindings**. `x = 1` is undone; `x = [1]` followed by an error leaves the list object itself mutated if a later statement appended to it. |
| Deep snapshot every heap object reachable from globals | unbounded, and needs a GC to do it | Everything. This is a GC feature, not an M8 one. |
| **Run each line in a fresh child `Vm`, keeping only the serialisable state** | a process spawn per line | Everything, and kills the REPL. |
| **Accept the partial mutation and say so** | zero | Nothing, but the behaviour is *documented and predictable*. |

**Ruling: the globals-table snapshot, and the documentation states exactly what it does and does not
undo.** A REPL line that errors may have left mutations to *objects* it bound; it will not have left
*bindings* it did not complete. For the overwhelmingly common case — `x = 1; y = boom()` — this is
indistinguishable from a full rollback, and it costs one `Vec` copy per line. The honest alternative
(full rollback) is a GC-shaped problem and is deferred.

This is ruling 13 in §13, because it is the one place in this document where the simple design is
visibly an approximation, and a reviewer should decide whether the approximation is acceptable rather
than discovering it from a user's REPL session.

### 10.4 `bt` and the traceback

[`06-parser.md`](06-parser.md) §3.3 already fixes the traceback's data structure:

```rust
pub struct RuntimeError {
    pub kind: ErrorKind,          // TypeError, IndexError, KeyError, NameError, …
    pub message: String,
    pub span: Option<Span>,       // None for errors with no source location (OOM, host failure)
    pub frames: Vec<FrameInfo>,   // innermost first
}
```

`FrameInfo` is `{ function: Arc<str>, span: Option<Span>, line: u32 }` and is built **at the `THROW`
site**, by walking `vm.frames` once. That walk is the only place in the VM that allocates a `Vec`
on an error path, which is acceptable: an error is already allocating a `String` for its message.

**The span comes from the compiler, not the line table.** [`06-parser.md`](06-parser.md) §3.3.3
rules that "the compiler records, for every instruction that can raise, the `Span` of the AST node
it came from" and that "the VM's error path pops the span from the frame." So `Frame` needs a span
cursor, and the bytecode needs a span table:

```rust
/// Per frame, a cursor into the proto's span table. Advanced lazily: the
/// dispatch loop does NOT advance it per instruction (that would be a
/// compare and a branch on the hot path). Instead, the error path binary-
/// searches `proto.spans` for the span covering `pc`. A binary search over
/// ~100 entries is 7 compares, and it only happens when an error is raised.
pub struct Frame {
    // …
    /// The proto's span table, for the error path only.
    spans: *const SpanEntry,   // non-null while the frame is live
    span_len: u32,
}
```

This costs **zero instructions on the happy path** — the binary search is off the loop — and it
buys exact spans for errors, which is the whole point of §3.3.3 of the parser plan. The
`SECT_LINES` table in the `.zeno` file remains for the **binary** (a traceback in a compiled
program, where the source may not be present); the span table is in the file too, and is larger,
which is why `HAS_DEBUG_INFO` covers both and a release `.zeno` drops both.

### 11.4 Group 4 — differential and fuzzing

**Differential.** Every file in `tests/cases/` runs through the M3 tree-walker and the M4 VM; stdout,
stderr, and the *sequence* of errors must be byte-identical. This is the oracle
([`00-blueprint-review.md`](00-blueprint-review.md) A6: "M3 is not throwaway: it is the
differential-testing oracle for M4 onward"). The harness compares **error messages and spans**, not
just output, which is what forces the span table of §10.4 to actually be right.

**Fuzzing.** Three fuzz targets, all in `crates/zen-vm/fuzz/`:

| Target | Input | Oracle |
|---|---|---|
| `fuzz_bytecode` | arbitrary bytes, treated as a `.zeno` payload | the loader either rejects it or the VM runs it to completion. **Never a panic, never a hang, never OOM** — `max_depth` and the length checks bound the run. |
| `fuzz_zen_source` | arbitrary text, compiled then run | the compiler returns a `CompileError` or the VM runs it. No panic in either. |
| `fuzz_corpus` | a valid `.zeno` with 1–3 random bytes flipped | always rejected (CRC), or loads and behaves as a *different but valid* program. Never a wrong-index access. |

The `fuzz_zen_source` target is the highest-value one, because it is the only way to reach the
compiler/VM boundary with inputs no human would write, and the `CompileError` path in the bytecode
plan (§4.2) is the code most likely to have an unhandled case.

**Implementation status (M1–M5 freeze audit).** The root `fuzz/` workspace (`cargo +nightly fuzz`)
holds three targets, all bounded by an explicit step budget so a non-terminating program returns a
catchable `NativeError` ("step budget exhausted") instead of hanging:

| Target | Input | Bounds |
|---|---|---|
| `value_fuzz` | arbitrary bytes through the M2 value/`ops` surface | pure, no execution |
| `interp_fuzz` | arbitrary text lexed + parsed + evaluated by the M3 tree-walker | `Interp::set_step_budget` |
| `vm_fuzz` | arbitrary text compiled + run on the M4 register VM | `Vm::set_step_budget` |

The budget is set by the host (`set_step_budget`), not by the fuzzer input, and defaults to
unbounded for normal embedding. A single repetition/padding allocation is capped at 256 MiB
(`ops::MAX_STRING_LEN`) so `"x" * 8**64` raises `ValueError` rather than aborting with
`allocation-size-too-big`.

Two findings are **known and accepted**, not bugs in the M1–M5 surface:

- **Reference cycles leak**, in both the interpreter and the VM, exactly as
  [`09-memory.md`](09-memory.md) §4.5 and [ADR-0002](decisions/ADR-0002-memory-model.md) specify.
  Run the fuzzers with `ASAN_OPTIONS=detect_leaks=0`; LeakSanitizer otherwise reports these by design.
- **Aggregate allocation is unbounded** (no `--mem-limit` yet, §11.5 test 33), so a long-lived
  fuzz process grows RSS and libFuzzer eventually reports `out-of-memory`. This is **M9** work,
  not a VM defect. Run with `-fork=1` (or a raised `-rss_limit_mb`) so the leak is not attributed
  to an input.

The `fuzz_bytecode` and `fuzz_corpus` targets are blocked on the `.zeno` bytecode format/serializer
(§4.2, M8) and are deferred until it exists.

### 11.5 Group 5 — memory and stability (6 tests)

| # | Test | Asserts |
|---|---|---|
| 30 | 10⁷-iteration loop that allocates and drops | **flat RSS** after warmup ([`00-blueprint-review.md`](00-blueprint-review.md) §5.6). Sampled every 10⁶ iterations. |
| 31 | 10⁷-iteration loop of closures that capture | every captured cell is dropped; the open-upvalue list is empty at the end |
| 32 | a closure created inside a `try` whose frame is unwound | the cell is `Closed`, and the closure still returns the right value — the §5.4.2 use-after-free class |
| 33 | `zen --mem-limit 64M` on a deliberate OOM program | a clean message and a non-zero exit, not an abort (§4.6) |
| 34 | an error raised 10⁵ times in a loop | `vm.frames.len()` and `vm.handlers.len()` are back to their pre-loop values. **A handler leak is a slow OOM and this test is how it is caught.** |
| 35 | every test in groups 1–4 under `--release` **and** under debug | the §4.5 depth difference is asserted, not assumed |

### 11.6 The M4 exit criterion

1. Groups 1 and 2 pass completely: 30 tests.
2. All 32 files of `tests/cases/` run through the VM with byte-identical output to M3, including
   error messages and spans.
3. The three fuzz targets run for 6 CPU-hours with zero findings.
4. Group 5 passes, and `bench_core` meets the §12.1 gate.

Group 3 is explicitly **not** in the M4 criterion — it is M5. M4 ships with `vm.ic` allocated,
`ic_poly` reserved, and every `IC_*` opcode armed but permanently missing, which is a valid state:
the compiler emits `IC_*` only behind the M5 feature flag.

## 12. Performance notes

### 12.1 The gate, restated with the protocol

> **Zen must be at least 1.5× faster than CPython 3.13 on the aggregate of `bench_core`, and never
> slower than CPython on any individual benchmark in that group.**

Copied from [`00-blueprint-review.md`](00-blueprint-review.md) §4 because a gate is only real if the
measurement is pinned. The protocol:

| Requirement | Value |
|---|---|
| Build | `cargo bench --profile bench`, i.e. `opt-level = 3`, `lto = "thin"`, `codegen-units = 1`, **`debug = 1`** (`zen/Cargo.toml:52-58`) |
| PGO | **on**, per §3.3. The non-PGO number is recorded in the report but is not the gate. |
| Zen invocation | `./zen/bench_core <name> <iters>`, no `--check`, no debug info, stdout to `/dev/null` |
| CPython invocation | `python3.13 -X importtime bench.py <name> <iters>`, same machine, same governor |
| Machine state | `performance` governor pinned, turbo pinned to its base clock, no other load, 5 repetitions, **median** reported |
| Per-benchmark time | 10⁶–10⁹ iterations, chosen per benchmark so each run is 1–10 s |
| Warmup | 10⁵ iterations discarded before timing |
| Comparison | the ratio of Zen to CPython time; the gate is the **aggregate** (geomean) ≥ 1.5 and **every** individual ratio ≤ 1.0 |
| Baseline drift | CPython's time is re-measured every run. A Zen "win" achieved by a slow CPython run is a bug in the harness, so the report prints both raw times, never only the ratio. |

**The "never slower individually" clause is the one that will be argued about**, because three
benchmarks are *known* to be hard ([`00-blueprint-review.md`](00-blueprint-review.md) §4):
`bench_json_parse`, `bench_startup`, and `bench_closure_alloc`. Each has a stated mitigation in
that table, and the clause is not waived for any of them. If `bench_json_parse` cannot be beaten
with a Rust parser, the answer is to be honest and re-scope the benchmark, not to move it out of
`bench_core` — that would be gate-shopping, and §13 lists it as a ruling for the reviewer.

### 12.2 Where the time goes, per instruction class

The dispatch loop is ~4–6 cycles per instruction (§3.3), so the interesting question is not "how
fast is dispatch" but "how many instructions and how many cache misses per operation". This is
where the register design pays:

| Operation | Instructions | Cache lines touched **[E]** | vs a stack VM |
|---|---|---|---|
| `acc = acc + i` | 1 | 1 | 3–4× fewer instructions |
| `list.append(x)` | 2 (`IC_INC`-style len bump + store) | 2 | 2× fewer; the old VM needed `DUP_TOP; BUMP_LIST_LEN` |
| `d.a` (monomorphic) | 1 | 1 | ~5× fewer, and no hash |
| `d[k]` (dynamic key) | 1 + hash | 2 | **same** as a stack VM — the honest limit |
| `f(a, b)` | 2 (2 `MOVE`s + `CALL`) + callee prologue | 1 | ~2× fewer; no push/pop pair per arg |
| `s + "x"` in a loop | 1 + alloc + 2 memcpy | 3 | **worse than CPython's `+=`** until the M11 JIT; see below |
| `for x in list` | 3 (`ITER_INIT`, `ITER_DONE`, `ITER_NEXT`) per element | 2 | same count, but no per-element bounds check |

**The string case is the one that will fail the individual-benchmark clause first**, and it is
worth pre-analysing. CPython's `s += "x"` is amortised O(1) because `str` is mutable and refcount-1.
Zen's `s` is immutable and `Arc`-backed, so `s + "x"` allocates and copies every time — O(n²) for a
loop. The honest options, in the order they should be tried:

1. **M11's JIT with a string-in-place guard**: the translator emits an in-place append when the
   `Arc` refcount is provably 1. This is a real optimisation, it is real work, and it is the
   right answer.
2. **A `rope` type for concatenation**, untagged until the flatten is forced. A large design change
   that changes `==` semantics risk; rejected.
3. **Accept it and re-scope the benchmark.** `bench_string` should measure what a Zen program
   actually does — build with `+=` in a local, or join a list — and the quadratic case should be a
   *documented* language characteristic, not a gate failure. This is the option most likely to be
   taken and the one most worth arguing about, so it is on §13.

### 12.3 The benchmark table, with the expected bottleneck for each

All Zen figures are **[T]** targets. None is **[M]**, because the VM does not exist.

| Benchmark | Expected bottleneck **[E]** | Target vs CPython **[T]** | Gate clause |
|---|---|---|---|
| `bench_loop_sum` | dispatch. Nothing else. | ≥ 8× | individual ≤ 1.0 |
| `bench_list_ops` | `Vec` growth + `Arc` refcounting on the list object | ≥ 3× | individual |
| `bench_dict_ops` | hash function; ICs do not help dynamic keys | ≥ 1.8× | individual |
| `bench_field_access` | **IC + shape slot load** | ≥ 6× | individual |
| `bench_method_call` | `Frame` push/pop + `Arc` clone of `self` | ≥ 3× | individual |
| `bench_closure_alloc` | one `Closure` allocation + `Arc` per upvalue | ≥ 1.5× | individual — **known hard** |
| `bench_string_build` | allocation + memcpy per `+` | ≥ 1.0× | individual — **known hard, see §12.2** |
| `bench_iteration` | `IterState` allocation per loop, 1–2 per loop entry | ≥ 3× | individual |
| `bench_json_parse` | our parser vs CPython's C extension | ≥ 1.0× | individual — **known hard** |
| `bench_startup` | process exec + dynamic linking | ≥ 0.8× | individual — **known hard** |
| `bench_recursion` | `Frame` push/pop, or `TAIL_CALL` | ≥ 10× | individual |

The three **[T]** targets in the "known hard" rows are set at or near parity deliberately: a target
of 3× on `bench_json_parse` would be fiction. The gate is the aggregate, so three near-parity rows
must be carried by the other eight — which is exactly the trade the aggregate clause was designed
to make visible.

### 12.4 Instrumentation, because guessing is how milestones slip

Three levels, all behind features, none in a release build's hot path:

| Level | Flag | What it gives |
|---|---|---|
| Counters | `zen-perf` | Per-opcode dispatch counts, IC hit/miss/megamorphic counts, shape transitions, allocations by kind, frame push/pop. A `Vec<u32>` of 256 counters indexed by `op`, incremented in the dispatch arm. **This changes the dispatch cost by ~1 % and is therefore only ever enabled for a diagnostic run.** |
| `perf record` | always available | The real answer for "where is the time". `perf stat -e instructions,branches,branch-misses,cache-misses` on `bench_core` is the PGO input and the regression detector. |
| Counters + `perf` together | `zen-perf` | The only way to distinguish "the loop is dispatch-bound" from "the loop is allocation-bound", which look identical in wall time. |

**The single most useful diagnostic** is `branch-misses / branches` on `bench_core`. Above ~5 %, the
PGO profile is stale or the opcode mix has shifted and the jump table needs re-sorting; below ~2 %,
dispatch is not the bottleneck and the time is elsewhere. That single ratio, plus allocation counts,
is enough to diagnose the VM's performance without writing a profiler.

### 12.5 What will be slower than CPython, honestly

- **Startup**, until the native-module graph is lazy (§12.3). A Rust binary with tokio + reqwest
  linked in reaches `main` in ~5–15 ms; CPython reaches its first bytecode in ~15 ms. Parity is the
  target, not a win, and it is a real constraint on dependencies, not on the VM.
- **Cold `dict` access in a shape-unstable program**, which is the same hash CPython uses. The win
  from shapes is entirely in the shaped case; a program that never reuses a key gets nothing.
- **`bench_closure_alloc`**, because `Arc` + CoW refcounts on every store
  ([ADR-0002](decisions/ADR-0002-memory-model.md)) and CPython's `dict` is mutable and unrefcounted.
  The ICs help the *field* access; they do not help the *allocation*.
- **Anything dominated by syscalls.** Zen will never beat CPython at `bench_http` and does not try
  to; those benchmarks exist to prove no regression, not to win.

## 13. Rulings a reviewer should double-check

Ordered by how much damage getting them wrong would do. The first four are load-bearing for
everything else.

| # | Ruling | Where | Why it might be wrong |
|---|---|---|---|
| 1 | **No panics, and OOM is the one fatal exception** | §4 | The no-panic rule is a policy from [`00-blueprint-review.md`](00-blueprint-review.md) §5.1, so the interesting question is §4.6's carve-out. If a reviewer wants OOM catchable, it costs 5–10 % on every allocation. The alternative view is that "no input can abort the process" is worth any price. **This is the single most contestable decision in the document and it should be decided explicitly, not inherited.** |
| 2 | **256 registers, allocated once, and 64 would not be faster** | §2.3 | The argument is that untouched array space costs nothing, only touched cache lines do. That is right for functions with few live registers and **wrong for a function with 200 live locals in a loop**, where the array is genuinely 200 registers wide and the `u16` encoding would be a genuine win. The mitigation is spilling, not a smaller array. **Measure the live-register p99 across the stdlib.** |
| 3 | **`match` dispatch, never computed goto, with PGO as the answer** | §3.3 | If PGO cannot hold branch misses under 5 %, a computed-goto dispatch via inline assembly becomes worth its cost, and that is a real fork. It is also not available in stable Rust, so the fallback would be a nightly dependency or a hand-written `asm!` block per opcode. **The 5 % branch-miss number from §12.4 is the decision point and it does not exist yet.** |
| 4 | **The `get_unchecked` on the register file, justified by load-time validation** | §3.2 | Every bounds check is removed from the hot path on the strength of a validator that must be complete and correct for all 111 opcodes. A missing check in `validate()` is a **soundness** hole, not a robustness one. The mitigation is the 12 tests in §11.2 and the crate-level lint banning raw indexing. **A reviewer should read `validate()` against the opcode table, line by line.** |
| 5 | **Zen exceptions do not use Rust unwinding** | §4.1, §5.4 | The alternative — `catch_unwind` with a payload — is dramatically less code and gives correct `finally` semantics for free. It was rejected because a panic-based mechanism makes "did this unwind through a `Drop` that can panic?" a permanent concern, and because the legacy sentinel-string design shows what happens to a global error channel in a 10 000-line interpreter. **The trade is ~200 lines of table-driven code for the absence of a whole class of interaction bugs.** |
| 6 | **Stack overflow is a frame counter at 8192, not a guard page** | §4.5 | A counter is a policy number; a guard page is a hardware guarantee. The counter's only risk is that native stack use per Zen call exceeds the 900 B assumed, which would mean a real segfault before the counter fires. **Test 35 exists for exactly this, and it must be run under an 8 MiB `ulimit -s`, not just at the default.** |
| 7 | **Monomorphic → 2-entry polymorphic → permanently megamorphic** | §6.3 | The 2-entry cap and the permanent give-up are both heuristics. A site that is megamorphic in a warmup phase and monomorphic in a steady phase is stuck on the slow path forever. The alternative — a periodic re-probe — is unbounded work for an unproven benefit. **Test 24 asserts the cost is within 5 % of no-IC, which is the actual requirement, and the thresholds could be retuned against `bench_field_access`.** |
| 8 | **Linear scan for ≤ 8 fields instead of a hash** | §7.3 | The crossover estimate (~12) is reasoned, not measured. If the real crossover is 5, every dict with 6–8 keys is doing 8 compares where a hash would do 1. **§12.3's 4/16/64/1024-key benchmark is designed to find this, and a 4-wide SIMD compare is the fallback.** |
| 9 | **Shapes interned globally and never evicted** | §7.1 | This is the decision most likely to need a follow-up. A program that genuinely creates a new shape per object grows `vm.shapes` without bound, and there is no eviction. `Unshaped` and `--mem-limit` contain the damage but do not fix the cause. **A shape cache with a weak-ref eviction policy is the most likely M5 follow-up and is deliberately not designed here.** |
| 10 | **`string`/`bytes` are `Arc`-backed, so `s + "x"` is O(n) in a loop** | §8.2, §12.2 | The alternative — a mutable, refcount-1-only string with in-place append — is what CPython has and would beat it on `bench_string_build`. It was rejected because it makes the value's identity depend on its refcount, which is exactly the kind of context sensitivity that produces hard bugs. **This ruling is the direct cause of the most likely individual-benchmark gate failure, and the M11 in-place-append guard is the planned fix.** |
| 11 | **The panic hook as a net, with exit code 101** | §4.7 | Converting a panic into a "Zen error with a non-zero exit code" as §5.1 requires is fine, but distinguishing 101 from 1 means a crashed run and a script error are different in the shell. `zen test` treating 101 as a failure is the important part and is easy to get wrong. |
| 12 | **A per-`Vm` inline cache table, no sharing between threads** | §6.4 | Warm-up cost is paid per thread, so a heavily-threaded program with a hot field access pays N warmups. The alternative — a shared atomic cache — reintroduces contention on the hottest path in the VM. **Per-thread is almost certainly right, but it is a trade of warm-up for steady state and a thread-local workload would expose it.** |
| 13 | **The globals snapshot per REPL line restores bindings, not object contents** | §10.3 | This is an approximation, stated as one. Full rollback needs a deep snapshot of everything reachable from globals, which is a GC capability and not an M8 one. A user who writes `x = [1]; x.append(2); boom()` sees a mutated `x` after the error. The alternative — accepting the partial mutation with no snapshot at all — is also defensible and is 1 µs cheaper per line. **Decide whether bindings-only rollback is good enough, rather than inheriting it.** |
